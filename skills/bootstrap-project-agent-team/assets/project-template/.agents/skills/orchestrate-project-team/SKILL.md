# 编排项目 Agent 团队

把角色能力与工作状态分开：角色固化在 `.codex/agents/`，路由保存在本机注册表，进度与证据保留在任务消息中。管理、开发、验收构成最小交付闭环；总控负责团队拓扑，调研负责事实证据，均按需启用。

跨任务协作前，必须阅读 [协议](references/protocol.md)。

## 选择动作

- **调整团队**：用户明确要求增加、减少、复制或重定义 Agent 时，由总控 Agent 执行拓扑变更。
- **讨论版本**：只在管理 Agent 中澄清目标，不启动开发。
- **启动版本**：用户明确确认版本已定并要求开始时，执行运行闭环。
- **查询状态**：读取相关任务的最新状态并按 work_item 汇总，不发新指令。
- **一次性并行任务**：无需长期记忆时生成项目级 subagent；完成后等待并关闭，不写长期注册表。

不要因为“多 Agent”而默认增加角色。只有存在真实并行、上下文隔离或独立验收收益时才增加。

## 调整长期团队

1. 读取当前项目路径、`.codex/config.toml`、所需 Agent 配置、注册表和现有任务列表。
2. 使用规范标题：`<项目名> · <角色> Agent`。标准角色为总控、管理、调研、开发、验收。
3. 按标题和项目路径查重。恰好存在一个同角色任务时复用；存在多个时停止并请用户选择。
4. 只有用户明确要求时才创建、复制、重命名、归档或减少长期任务。不要指定模型或推理强度。
5. 长期团队共享同一代码状态；同一时刻只允许开发 Agent 写业务文件。
6. 新角色初始化必须读取对应 `.codex/agents/*.toml`、本 Skill、协议和根目录 `AGENTS.md`；初始化轮禁止业务工作和文件写入。
7. 将真实 ID 写入 `.codex/team/registry.local.json`，不得写入可复用 Skill 或可提交配置。
8. 新增角色向总控发送 `TEAM_READY`；总控广播 `TEAM_UPDATE` 并回报 `TEAM_CHANGED`。
9. 任一握手失败时停止，不启动业务。

## 运行版本闭环

1. 确认用户已给出明确目标并明确说可以开始。未确认时只把内容发给管理 Agent 讨论。
2. 读取本机注册表；缺失或失效时用任务列表按规范标题和项目路径恢复。未经同意不要补建任务。
3. 生成稳定 `work_item`，建议 `V-YYYYMMDD-<slug>`；后续消息沿用同一 ID。
4. 向管理任务发送 `WORKFLOW_START`，包括用户原话、范围、约束、非目标和已知验收要求。
5. 存在关键事实缺口时，先发送 `RESEARCH_REQUEST`；管理 Agent 核验证据后才形成实现契约。
6. 管理 Agent 向开发发送 `IMPLEMENT_REQUEST`；开发完成后向验收发送 `VERIFY_REQUEST`。
7. 验收返回 `FAIL` 时，只修复有证据的问题，保持 work_item 并递增 iteration。
8. 连续三轮验收失败、标准矛盾、写入冲突、权限不足或需要外部不可逆操作时，发送 `BLOCKED` 并升级给用户。
9. 仅当验收返回 `PASS` 后，由管理检查范围并发送 `VERSION_DONE`。
10. 使用 `wait_threads` 等待状态变化，最终汇总结果、测试证据、剩余风险和相关任务入口。

## 路由、权限与收口

- 任务消息历史是审计日志；不要额外写流水账文档。
- 使用注册表 ID 路由，标题只用于恢复与人工识别。
- 每条消息包含协议版本、message_id、work_item、from、to、type、iteration、summary、evidence、next_action。
- 重复 message_id 必须幂等，不重复实施或验证。
- 任何文档写入、长期任务变更、部署、发布、删除、付费和外部通知均需对应授权。
- 只有总控处理团队拓扑；管理不得修改团队，开发不得自我验收，验收不得修改实现。
- 长期任务完成版本后保持 `idle`；一次性 subagent 完成或失败后必须收口并关闭。
