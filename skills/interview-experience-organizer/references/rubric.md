# 面经整理规则

## 1. 问题抽取

- 把面试官连续追问合并为一个 Q，保留核心上下文。
- 如果同一问题下有多轮澄清，Q 中写成“主问题 + 追问：...”，不要拆成多个孤立小题。
- 候选人反问面试官的信息单独放入“候选人提问环节”。
- ASR 记录中常见“说话人1/2/3”时，根据语境判断身份；不要把寒暄、设备调试、无意义噪声整理为正式问题。

## 2. 真实回答 A 的处理

保留：
- 候选人的真实论证过程、表达顺序、关键数据、项目细节。
- 犹豫、绕路、被动确认等会影响复盘判断的表达。
- 面试官追问后候选人补充的信息。

清理：
- 重复口头禅，如“然后然后”“对对对”“嗯嗯”。
- 明显 ASR 错字，如 `AR` 常为 `AI`，`PS engineer` 常为 `Prompt engineer`。
- 断句混乱时可分段或编号，但不要改写成过度完美的版本。

## 3. 可改进点判断

优先识别这些高频问题：

- **没有结论先行**：先铺垫背景，最后才回答核心问题。
- **没有正面回答**：面试官问定位、角色、分母、结果，回答却在解释背景。
- **数据口径不清**：百分比、占比、转化率、GMV、准确率没有分母、时间窗口或对比基线。
- **角色贡献不清**：只说“参与/推动”，没有说自己负责调研、方案、协调、上线、复盘中的哪一段。
- **背景不服务理解**：不是所有背景都要删。业务模式陌生、复杂或强依赖后文理解时，必要背景应保留；只有背景与问题无关、重复，或迟迟不落到个人动作时才判为问题。
- **业务功课不足**：对目标公司、岗位、竞品或行业只有泛泛了解。
- **表达被动防守**：面对质疑时急于否认或“甩锅”，没有先认同问题再给方案。
- **暴露不足无方案**：说“没做”“不了解”“没跟进”，但没有补充后续规划。
- **技术细节不足**：AI 项目只说用了 AI，没有说明 Prompt/数据/评估/兜底/迭代。
- **候选人提问敏感**：问题像是在质疑公司，而不是请教产品取舍或业务逻辑。

每条可改进点写成“问题 + 影响 + 改法”，避免只写“表达不清晰”。

## 4. 参考回答写法

参考回答优先做“原回答的结构化版本”：保留候选人的核心论点、项目事实、表达策略和关键数据；不要随意把答案改成另一个故事。只有原回答明显错误、过度风险或缺少关键闭环时，才补充新内容，并尽量用“可以补充为/更稳妥的说法是”来表达。

通用结构：
1. 一句话结论。
2. 2-4个分点说明动作或判断。
3. 补充关键数据和口径。
4. 最后一句给反思、迁移价值或下一步。

如果业务背景是理解答案的前提，可以先用1-3句交代背景，再给结论和动作。

格式要求：
- 参考回答必须按语义分段，不要写成一个长段落。
- 常用分段方式：结论/背景一段，动作/方案一段，结果/反思/迁移价值一段。
- 每段通常1-3句；若超过4句，优先拆段或改成清晰分点。

项目题：
- 用“我负责什么 -> 发现什么问题 -> 做了什么方案 -> 怎么验证 -> 结果如何”。
- 业务背景按理解成本决定：陌生业务或特殊交易机制可保留2-4句；常见业务用1-2句。背景必须服务后续动作，不要机械压缩。
- 尽量出现“我”的动作，如“我主导梳理”“我设计”“我协调”“我复盘”。

场景题/数据分析题：
- 先给框架，如“我会从样本、功能、模型三个维度分析”。
- 再讲假设、验证方式、可能决策。
- 如果有实验设计，优先写随机对照、分层分析、漏斗拆解、case 归因。

业务理解题：
- 按“业务本质 -> 用户/商家画像 -> 关键链路 -> 竞品差异 -> 岗位适配”回答。
- 不懂时不要只说不了解；说“我目前理解到的部分是...下一步会重点验证...”。

AI 产品题：
- 讲清楚用户问题、AI 工作流、数据输入输出、评估指标、失败兜底。
- 涉及模型局限时，转化为产品设计方案，如置信度阈值、人工审核、样本外测试、Prompt 校验、日志反馈闭环。

职业规划/离职原因：
- 避免“补充简历”“镀金”等表达。
- 转成“希望在相关业务场景继续验证能力”“补齐某类产品经验”“岗位与过往经历匹配”。

## 5. 追问预测

从四类来源生成：
- 已被问到但没讲透的项目细节。
- 面试官明显感兴趣或反复追问的业务模块。
- 岗位 JD 对应的核心能力。
- 候选人回答中的薄弱点或数据口径缺口。

每个方向给具体问题，不要只写“项目细节类”。

## 6. 完成前检查

- 每个正式面试官问题都有 Q、A、可改进点、参考回答。
- 参考回答没有编造无法确认的数据。
- 自我介绍和项目数据与简历/个人口径一致。
- 综合评价覆盖项目、业务、AI/技术、数据、表达、主动性。
- 核心改进点能转化为下一场面试前的具体练习任务。
