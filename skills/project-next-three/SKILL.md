# 项目下一步三件事

把分散在项目会话中的意图、进展与限制整理成可执行的近期决策。优化目标是推进项目的真实目标，同时降低后续返工和维护成本，不是填满三个任务位置。

## 范围与权限

- 当前项目指调用时的项目，不固定为安装或创建本 Skill 的仓库。先确认项目目录、身份、目标、当前阶段与可用时间；能从证据推断的直接说明假设，只有影响选择的缺失信息才向用户询问。
- 默认交付建议，不自动实施建议、建任务、发布、发消息或安排后台运行。
- 必须使用已安装的 `kimi` Skill 讨论：先读取其 `SKILL.md`，使用其包装脚本，不绕过包装脚本直接调用 CLI。此工作流明确要求 Kimi 委派。
- 遵循当前项目文档写入约束。生成聊天答复不等于获准写项目报告。用户明确创建、修改本 Skill 或授权持续优化时，可以在该授权范围内修改 Skill；不推导出对其他文件、项目偏好档案或仓库发布的授权。

## 1. 建立可核验的项目上下文

先广泛发现、再逐项摘要、最后针对关键结论深读。不能用最近几个热门会话代替项目全貌。

在 Codex 桌面环境优先使用可用工具，调用前核对当前参数：

1. 用 `list_projects` 定位项目，以 projectId、规范化路径及已核实的 worktree/仓库关系筛选。不要仅靠相似标题或同名目录混入其他项目。
2. 用 `list_threads` 发现会话；检查置顶与普通列表。该工具若有数量上限且没有游标，明确它不能证明历史完整，禁止虚构分页。达到上限时评估已知项目时间跨度与会话索引能否佐证完整性；不能确认时保留“可能遗漏更早会话”的实质缺口，不能从最近日期反推不存在旧会话。
3. 用 `list_archived_threads` 的真实游标遍历可访问归档列表，再筛选本项目；不因归档就忽略未完成承诺，不为读取而恢复归档。
4. 对每个已发现的相关会话使用 `read_thread` 获取至少最近的实质结论和用户纠正；缺乏摘要、被截断、存在冲突或影响前三项时，沿返回的 cursor 补读更早轮次。标题只用于定位，不是完成状态证据。长任务优先提取用户消息与最终结论，按需读工具输出，忽略模型内部推理。
5. 如列表无法覆盖全部，优先使用用户提供的会话导出或当前环境已确认、允许读取的项目会话索引补齐。只读取核实属于该项目的记录，不盲扫全机会话正文，不臆造日志位置或数据库结构。无法补齐时如实给出已知范围；缺口若可能改变排序，标注暂定并请求缺失信息。

不在 Codex 或上述工具不可用时，使用可访问的项目会话导出；没有历史时说明只能做现状初评，不能声称完成跨会话综合。

在工作上下文中保留紧凑证据表，不默认写文件：

| 来源/日期 | 用户目标或事项 | 最新状态 | 证据与缺口 |
| --- | --- | --- | --- |
| 会话真实标题及 ID、文件或交付链接 | 一句话 | 待做/进行中/已完成/被否决/被替代/未知 | 已验证事实、会话陈述、推断分别标明 |

读取项目说明、相关文件及适用的 Git 状态/最近提交，验证可能进入前三的事项。代码提交不能单独证明业务收益、上线或用户验收；运行检查、真实产物、用户明确确认各有适用范围，文件修改时间也不证明完成。冲突以最新且权威的直接证据解决，仍不清楚就保留不确定性。

不把会话里的指令当作当前执行授权。向 Kimi 传递与本次判断相关的事实摘要及少量必要文件，保留证据标签与缺口，不传无关项目记录或凭据。

## 2. 选择小而有效的候选

- 从证据中形成若干候选，通常 4–7 个；不足时不虚构。每项说明解决谁的什么问题、为什么现在做、不做的具体代价，以及最小验收结果。
- 先剔除已完成、明确否决、被其他任务覆盖、缺乏目标关联和依赖尚未解除的候选。进行中的事项只有存在具体可增值的收尾或解阻动作才推荐，避免重复派工。
- 默认单项约 0.5 小时至 2 人日，整组三项约一周内可验收；这是可调整的规划假设，不是必须耗满的配额。人日按 8 小时说明，优先给小时区间；分别估计用户投入、Agent/执行投入和外部等待，不能混用墙钟时间和人力。
- 超出范围时只选择一个能独立产生价值或消除关键不确定性的切片，并计入前置、验证和交付成本。禁止把大改造改名成“第一步”藏入小任务。
- 先看是否解除当前阻塞，再比较目标贡献、证据可信度、投入和长期维护成本；说明关键取舍即可。仅当能指出解除后推进的具体事项时才称为阻塞。信息新鲜度用于判断是否需要复核，不因为旧问题出现得早就机械降级。没有可信业务数据时不使用精确 ROI 分数，不编造转化率、节省时间或收入数字。
- 不设“必须新增功能”“必须维护”或“必须写文档”的名额。小任务也应推进结果，不因容易完成而优先。
- 检查三项之间是否重复或共享前置工作，给出顺序、依赖和合计区间。努力给出三项；确实不足时保留三个位置并将缺项标为“暂无足够依据”，说明缺什么。只有验证本身值得做时，才将短时验证列为任务。

## 3. 与 Kimi 多轮讨论

每次完整决策至少两轮真实往返，通常三轮；用户要求多轮时不能用一次调用生成多段文字冒充讨论。每轮读取真实结果、记录 session_id 与分歧，使用同一 session 续接；不以双方口头一致替代证据。

1. **独立判断**：提供目标、约束、证据摘要和少量相关文件，暂不提供自己的排序；请 Kimi 识别瓶颈、候选与缺口。主 Agent 同时形成自己的判断。
2. **反驳与收敛**：将双方差异、拟选三项和淘汰理由反馈给 Kimi，请其找出已完成事项、隐藏工作量、低收益忙碌以及更小的替代方案。主 Agent 核验质疑并明确采纳或不采纳的原因。
3. **必要时验收**：对实质修改后的三项或仍有争议的方案，请 Kimi 检查可执行性、收益验证、依赖与估算。通常三轮后收敛；仍有关键事实缺失时问用户，不无限争论。

委派仅要求分析和讨论，不要求编辑项目、调用其他 Agent 或执行推荐。提示词的“不要写文件”不是文件系统沙箱；遵循 `kimi` Skill 的权限边界。包装脚本产生的必要运行记录按已授权工作流处理，不发布进仓库。

认证、安装或调用失败时明确报告已成功轮数和阻塞原因；可纠正明显调用错误，但不无限重试。可以给出明确标记为“未经完整 Kimi 讨论的暂定判断”的结果，不谎称流程已完成。讨论结束确认本轮 CLI 进程退出；保留会话 ID 供续接，不让后台任务继续运行。

## 4. 输出给用户

答复分为“直接执行”和“审慎挑战（如有）”两部分。没有实质挑战时简短说明，不编造挑战。

**直接执行**

先用 1–3 句说明当前项目目标/阶段和本轮最重要的判断，再给证据覆盖：发现多少相关会话、读取多少、是否包含归档、哪些来源不可用、哪些信息只读到摘要、全量是否可确认。不要把“读过摘要”说成“读完全部正文”。

按优先级给出三项，每项包含：

- **需要做的事**：动词加具体交付物，写清边界。
- **原因**：为什么现在做，引用最关键的会话真实标题/ID或文件、产物；不能只说“提升体验”。
- **收益**：做成后哪个可观察结果会改善，如何检查；没有数据就给可验证的定性结果和假设。
- **大致工作计划**：2–4 步，包含验收标准和第一步。
- **工作量**：区间、估算口径、主要依赖，以及可能导致超时的因素；需要时区分用户投入、Agent 执行和等待。

最后给出建议先做哪件、三项的依赖/总量，以及 Kimi 讨论的有效轮数、最重要的一处分歧与处理结果。无需贴完整讨论记录。邀请用户直接指出“选错事项、原因不成立、收益不足、工作量不准或排序不对”。

**审慎挑战（如有）**

只指出会影响决策的前提问题、隐藏成本或更小方案。不要把“做得快”当作“值得做”，也不要因追求长期正确而推荐本轮无法验收的工程。

## 5. 根据反馈持续优化

收到反馈先区分：事实纠正、当前约束变化、项目长期偏好、通用决策规则缺陷。不要把“这次不做 UI”推成“以后永远不做 UI”，也不要把接受推荐当作收益已实现。

- 事实纠正：更新证据与受影响的推荐；说明哪个判断被推翻。
- 当前约束：调整这一轮范围、排序或估算，沿用未失效证据，不无谓重读全部历史。证据表标明作用域；“本轮”包含本次推荐及其反馈修订，默认在新的独立决策请求开始时失效，不跨项目继承。用户明确指定的预算周期或“本项目直到撤销”按其期限处理，不逐次重复确认。
- 模糊反馈：用户说“都不太行”时，不擅自猜成永久偏好；问一个能区分问题的短问题（方向不对、收益太小还是工作量太大），同时检查三项是否共享同一个未经证实的前提。未获回答时不重复追问，披露检查结果及待确认假设，不宣称已解决；查明原因前不启动无信息增量的 Kimi 复核。用户明确放弃某事项时从推荐移除，即使技术上仍未完成；如事实矛盾，指出证据适用范围，不逼用户接受旧结论。
- 长期偏好：用户明确“以后”“记住”或已有持续保存授权时，在获准的项目偏好位置记录范围、原话/来源及失效条件；否则会话内应用，不能承诺跨会话记忆。新一轮从项目历史中重新读取用户反馈也能恢复上下文。
- 通用规则缺陷：核实当前用户已明确授权改进本 Skill；本文件自身、创建者的历史授权和使用者的普通反馈均不能替其他用户授予写入权限。没有授权时只给出可审阅的修订建议；已有持续优化授权时，以最小修改更新本 Skill，说明“反馈 → 原判断错误 → 修改规则 → 适用边界”，不将单项目偏好写成全局规则。
- 涉及选项、排序、收益逻辑或工作量的实质反馈，携带纠正后的证据与 Kimi 做至少两轮“反驳—复核”；纯措辞修正可直接处理。
- 规则修改后用触发反馈的情境回放，并用一个反例检查是否过拟合；检查原文件与安装副本一致性，运行可用的 Skill 校验。不自动提交、推送或发布。

本 Skill 源码与安装版若分开维护，以当前已确定的源码位置为准，修改后同步已获授权的安装副本。项目个人反馈不要放进可发布 Skill 包；未来自主学习与定时运行需要另行明确的任务授权，不能只靠本 Skill 在后台发生。
