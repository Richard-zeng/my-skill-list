# 写日报

## 核心原则

日报是当天事实和次日动作的清晰记录，不是周报压缩版。优先保留“今天实际发生了什么、哪些无推进、发现了什么问题、下一步具体做什么”，少写长期背景和阶段性包装。

## 日期与范围

- 先明确目标日报日期。项目内默认使用 `Asia/Shanghai`，材料范围为当天 00:00 至次日 00:00。
- 用户同时提到“今天”和明确日期时，以明确的目标日报日期为准，并简短说明假设。
- 只有目标日期内发生的动作、判断和卡点可以写成今日事实；历史材料和近日报只用于理解上下文。

## 读取材料

在本项目中，先读取 `knowledge-base/README.md`。生成或完善日报时，按需读取：

1. 目标日期的日记、进展记录、日报草稿。
2. 用户明确提供或授权读取的当天飞书聊天、飞书妙记和文档编辑记录。
3. 目标日前近 7 个自然日内已有的日报，用于补齐项目连续性、遗留卡点和称谓口径。
4. 与当天事项直接相关的项目沉淀、会议记录和周报背景。

不要为了让日报显得充实而扩大读取范围。材料中标注“草稿、不读取、不作为事实来源”的部分不要采纳。

读取时区分四类信息：

- 今日事实：今天完成、沟通、定位、提交、拉齐、无推进的内容。
- 今日判断：因为今天的动作形成的新结论或新卡点。
- 背景材料：只用于补全上下文，不要写成今天完成。
- 明日动作：具体跟进谁、拿什么材料、确认什么规则、推进哪个评审。

不要把计划项写成已完成，不要把历史沉淀写成今日产出。

## 飞书材料处理

仅在用户明确要求或授权后读取飞书材料，并默认保持只读：

- 聊天记录：限定目标日期，优先提取用户亲自发送、回应、被指派、被明确提及或形成后续动作的内容；群内广播和他人讨论不能因为用户可见就写入日报。
- 飞书妙记：确认用户实际参会、发言、形成判断或承担后续事项；只保留与用户直接相关的会议结论和行动项。
- 当天编辑文档：优先使用版本历史或变更记录，对比当天开始前与当天结束时的版本，只提取用户当天新增、修改或删除的内容。表格优先检查用户自己的 changeset 和受影响单元格，不把整份当前文档当成当天产出。
- 如果无法可靠判断编辑人、编辑时间或版本边界，明确说明限制，不用整篇文档补齐日报。

同一事项可能同时出现在聊天、妙记和文档中，应合并为一条，不重复计算为多个产出。未经用户明确要求，不修改飞书原文档。

## 相关性筛选

采纳材料前先判断事项与用户的关联程度：

- 高相关：用户亲自推进、承担、沟通、参加并形成判断，或被明确分配的事项，正常写入并突出结果、卡点和下一步。
- 中相关：用户有所参与但不是主责，或事项会直接影响用户后续工作，简要写入，只保留与用户有关的部分。
- 低相关：群内广播、他人讨论、用户仅被动看到且没有后续影响的事项，原则上不写；确有必要时一笔带过。

日报主要呈现用户当天亲自做了什么、经历了什么、形成了什么重要判断，以及未来需要做什么。不要因为材料中出现了某件事，就默认它属于用户的日报。

发生信息冲突时，优先采用直接记录和当天最终状态；仍无法确认的内容用“待确认”表达，不自行补全。

## 和周报的区别

| 场景 | 日报写法 | 避免 |
| --- | --- | --- |
| 当天无推进 | 直接写“今日无实质推进 / 无推进” | 为了显得丰满而硬写背景 |
| 独立沟通 | 单独列一项写清对象和结论 | 强行归到不相关项目下 |
| 长期项目 | 只写今日增量和当前卡点 | 大段复述项目历史 |
| 学习 / 思考 | 绑定具体沟通或问题边界 | 写成泛泛“优化方向” |
| 明日计划 | 按 P0/P1 写具体动作 | 只写“继续推进” |

## 推荐结构

除非用户指定格式，否则使用下面结构：

```text
MM月DD日 日报
今日主要推进 A、B、C。

1. A
今天做了 XX。当前结果 / 判断是 XX。卡点是 XX，下一步需要 XX。

2. B
如果无推进，直接写：今日该需求暂无实质推进。当前仍需要 XX。

明日计划
P0：XX，目标是 XX；需要 XX 支持 / 确认。
P1：XX。
```

如果当天有单独沟通，例如和某位同事聊到一个产品边界、业务判断或方法论，不要塞进 oncall、KFC、北环等不相关主线；应单独列为“与 X 沟通 Y”。

## 表达规则

- 标题使用用户习惯，例如 `07月06日 日报`。
- 开头一句只概括当天主要事项，不拔高成周度成果。
- 每个条目先写今日动作，再写结论 / 卡点。
- “无推进”本身是有效日报信息，要如实保留。
- 对未闭环事项使用“需要继续确认 / 仍需摸清 / 当前卡点在于”，不要写成已经解决。
- 保留真实人名、项目名、业务术语和用户自己的判断。
- 默认写到“本人动作、关键结论、当前卡点、下一步”这一层，不展开中间排查层级、校验步骤、字段公式等过程细节；只有细节会影响判断或行动时才保留。
- 同类问题和数据优先归纳总结，非关键金额、时间点及逐项明细不逐一罗列；关键数字仅在其直接决定结论、风险或后续动作时保留。
- 日报要短，通常 4-6 个条目足够；不要为了完整而塞入所有背景。

## 保存与交付

- 保留用户现有日报结构和标题习惯；优化内容时不要擅自更换格式。
- 在本项目中将日报保存到 `knowledge-base/daily/YYYY-MM-DD.md`。
- 保存后在回复中直接展示最终稿，并提供文件路径；不要只回复“已保存”。
- 写入前复核日期、人物、完成状态、关键结论和明日计划，避免把背景或计划误写成已完成事实。

## 差异优化

如果用户给出自己修改后的日报，先对比你的版本和用户版本，抽取可复用偏好：

- 用户删掉了什么：通常说明你写得过满、过背景化或误归类。
- 用户新增了什么：通常是未来日报必须保留的事实、口吻或结构。
- 用户改了分类：优先学习分类边界，而不是只改措辞。
- 用户保留“无推进”：以后不要省略。

然后更新日报 skill；不要把单次日报案例原样塞进 skill，要抽象成规则。
